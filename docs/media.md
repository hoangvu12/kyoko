# Media

Images, avatars, emoji and stickers are fetched, decoded and cached in Rust (`crates/media`) and reach the window only as zgx host images (`ScriptHost::image`). zgx's own remote loader (`ui.image { src = "https://…" }`) is never used: it never evicts and spawns a thread per decode. The UI never touches the network; it asks for images by request and shows them by name.

## The gallery

`media::Gallery` is the one object the UI side talks to. It is `Send + Sync`, cheap to clone, and lives as long as the window.

- `Gallery::request(ImageRequest) -> ImageName` is cheap and safe to call on every render. It returns a stable name such as `media/3f2a…` and starts a load if the image is not resident. The window shows it as `ui.image { src = "host:" .. name }`. The same URL and variant always give the same name, and a signed attachment keeps its name when its signature is refreshed (the key ignores `ex`, `is` and `hm`).
- `ImageRequest` is a URL plus a `Variant`: a `SizeHint` in device pixels and a `Shape` (`Square`, or `Circle` for avatars, masked in Rust). A zgx node with `rounded` and `overflow = "hidden"` does clip images inside it, which is how the server rail rounds `Square` icons. `ImageRequest::from_message(Origin { channel_id, message_id })` marks an attachment so it can be refreshed.
- `Gallery::drain(now) -> Vec<Update>` runs on the UI thread. Each `Update::Show { name, pixels }` becomes `host.image(name, Some(ImageData))` and each `Update::Clear { name }` becomes `host.image(name, None)`. Pixels are an `Arc<[u8]>` shared with the gallery, so handing them to zgx copies nothing.
- `Gallery::set_waker(f)` is called whenever a drain has work: an image loaded or was evicted, or an animation frame is due. The desktop pushes into a `bridge::Inbox<()>` and a UI task drains the gallery on each wake.
- `Gallery::set_visible(names)` replaces the set of images on screen. Visible images animate and are never evicted. The desktop passes one union of everything on screen (the timeline's rows, the user panel avatar, the rail's icons, Luau's report); Luau can report a virtualized list's rows with `ui.call_sync("media_visible", names)`.
- `Gallery::set_hovered(name)`, `set_animations(Animations)` (a `Playback` each for GIFs and other animated images, emoji and stickers, told apart by the CDN path `/emojis/` or `/stickers/`; `set_playback` sets all three) and `set_reduced_motion(bool)` drive animation. Luau reports hover with `ui.call_sync("media_hover", name)` and the system's reduced-motion preference with `ui.call_sync("media_reduced_motion", ui.prefers.reduced_motion:get())`.
- `Gallery::status(name)` and `stats()` are for tests and diagnostics.

Request builders for what kyoko shows live in `bridge`: `avatar_request`, `guild_icon_request`, `emoji_request`, `attachment_request`, `embed_request` (embed images and thumbnails: through the media proxy with `width`/`height`, WebP unless a GIF; a WebP or a medium flagged animated (`flags` bit 5) adds `animated=true`), `gifv_request` (GIF embeds, below), `embed_icon_request` and `sticker_request` (below). In mock runs `bridge::local_media` sends every URL that is not on the mock server to its `/media/<hash of the path>.<ext>`, the same name oxidcord's mock resolver uses; the extension is the `format=` asked for, else the path's own when it is `gif`, `webp`, `png` or `json`, else `png`, and `animated=true` and `passthrough=true` are kept as the query. Mockcord answers a `.gif`, an `animated=true` `.webp`, a `passthrough=true` `.png` (APNG) and a `.json` (Lottie) with 8 animated frames whose first frame is the still it serves otherwise (`mockcord::MEDIA_FRAMES`), and `MediaFetcherBuilder::only_loopback` drops the Discord hosts from the mock fetcher, so a mock run never contacts Discord. The mock fetcher also speaks HTTP/2 with prior knowledge (`loopback_http2`, cleartext, which mockcord's server accepts), so mock media multiplexes over one connection as the CDN's does; mockcord records it (`MediaRequest::http2`). `avatar_request` falls back to the default avatar (`<cdn>/embed/avatars/<n>.png`) for a user without an avatar hash, as the web client does; mockcord serves those too. `bridge::media_fetcher` builds the fetcher from the fingerprint.

## Memory

Decoded frames are kept as RGBA in one LRU bounded by bytes: `DEFAULT_BUDGET_BYTES`, 128 MiB, set from `settings.media.memory_mb` and changeable with `Gallery::set_budget`. Every request and every visibility report makes an image the most recently used, so the order is "least recently shown". Over budget, the least recently shown images that are not visible go first, and the window is told to drop each one it holds. Visible images are never evicted; if the visible images alone exceed the budget, a newly loaded image that is not visible yet is dropped instead.

An animation keeps all its decoded frames only while they fit in an eighth of the budget (`ANIMATION_SHARE`). A larger one is streamed: the gallery keeps its first frame, its compressed bytes and its frame delays, and while it plays a `media-stream` thread decodes its frames again in order, one cycle after another, handing them over through a one-frame channel. It counts as the first frame times four plus its bytes; if even that exceeds the share it keeps its first frame only. Out of view or held still, the thread stops; playing again restarts it and skips to the frame it paused on. A frame that is not decoded by its time waits (8 ms polls) rather than being skipped. Frames are shrunk and masked as they are decoded (`media::Plan`), so a stream never holds the full-size frames. Decoding limits (32 Mpx per image, 500 frames, 64 Mpx across all frames, 64 MiB input) stop hostile files earlier. At most 4096 entries are remembered, failed ones included.

The on-disk cache (`<cache>/media/<2 hex>/<sha256>`) is pruned by the store, see `docs/storage.md`. The gallery tolerates it vanishing at sign-out: a missing file is a miss and the next write recreates the folder.

## Fetching and decoding

- One pooled `wreq` client from `net::client_builder(Destination::Image, ..)`, so CDN and GIF fetches present Chrome's TLS ClientHello and HTTP/2 settings, with an image's HEADERS weight (220), as the REST client does (`docs/fingerprint.md`, "TLS and HTTP/2 handshake"). HTTPS only (loopback HTTP for mockcord); every redirect is re-checked against the host allowlist and at most 5 are followed; bodies are capped at 64 MiB, whether or not the length is declared. An allowlist entry may name a port (`localhost:8443`), which only tests use; `MediaFetcherBuilder::trust` takes a test-only root the same way (`net::Trust`).
- Requests wait in one queue per host (`scheme://host:port`, `media::queue`), as Chrome's network stack does, and only the network fetch takes a place in it: the disk cache is read first and a hit never waits. Two requests for the same URL share one download.
- How many run at once on a host follows Chrome. Until the host's protocol is known, one request runs alone, so a cold burst opens one connection (wreq would otherwise start a TLS handshake per request and keep only the first that negotiated `h2`); the protocol is learnt from the first response's headers. On HTTP/2 up to 100 run at once over the one connection (`HTTP2_PER_HOST`): Chromium starts low-priority requests to a server that supports request priorities without the 6-per-host throttle (`services/network/resource_scheduler/resource_scheduler.cc`, `ShouldStartRequest` and `ReachedMaxRequestsPerHostPerClient`), and its HTTP/2 session allows `kInitialMaxConcurrentStreams` = 100 streams until the server's `SETTINGS_MAX_CONCURRENT_STREAMS` says otherwise, capped at 256 (`net/spdy/spdy_session.h` and `.cc`, Chromium main `be3c4d2`, read 2026-10-28). wreq's HTTP/2 layer honours the server's setting the same way, queueing streams beyond it. On HTTP/1.1, 6 per host (`HTTP1_PER_HOST`, Chromium's `kMaxNumDelayableRequestsPerHostPerClient`). A host idle for 90 s (the pool's idle timeout) is treated as unknown again, since its connection may be gone.
- Order: each load gets a `Ticket` when the UI asks for it, numbered in the order asked. A waiting request is started by rank, then number: user actions (`Rank::Urgent`: audio, Download, direct loads) first, then images on screen (`Rank::Visible`, from `set_visible`), then everything else asked for (`Rank::Asked`). An image that was on screen and left it before its fetch started is dropped from the queue (`Status::Dropped`); it is queued again, at the back, when it is asked for or shown again. An image never reported visible is never dropped. `MediaFetcher::waiting()` and `protocol(url)` are for tests and diagnostics.
- Decoding runs on the blocking pool, at most 2 at a time (`DEFAULT_DECODE_WORKERS`). PNG and APNG, JPEG, GIF, WebP and animated WebP decode with the `image` crate. Images larger than twice the hint are shrunk to it.
- Lottie JSON (stickers) is drawn by kyoko's own renderer (`crates/media/src/lottie.rs`, on `tiny-skia`): shape layers (groups, paths, rectangles, ellipses, solid and gradient fills and strokes, transforms with parents), precomps, solids, keyframes with their bezier easing and hold keys, hidden and matte-source layers skipped. Masks, mattes, trim paths, repeaters, stars, text and images are not drawn. It renders at the box size, at most 30 frames a second (`lottie::MAX_FPS`), as kept frames or a stream like any animation.
- An `ImageRequest` may carry a fallback (`ImageRequest::or_else(url)`): when the URL fails with anything other than an expired signature, the fallback is loaded under the same name. GIF embeds use it.
- A failed load is not retried for 60 s, unless it is a refreshable attachment (below).

Headers are Chrome's for an `<img>` on discord.com, from `Fingerprint::image_headers` (see `docs/fingerprint.md`): the Chrome user agent, `sec-ch-ua`, `sec-ch-ua-mobile`, `sec-ch-ua-platform`, `Accept: image/jxl,image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8`, `Accept-Encoding`, `Accept-Language`, `Referer: https://discord.com/`, `Sec-Fetch-Dest: image`, `Sec-Fetch-Mode: no-cors`, `Sec-Fetch-Site: cross-site`, `Sec-Fetch-Storage-Access: active` and `Priority: i`, in the order Chrome 156 sends them (`net::IMAGE_ORDER`), with HTTP/2 weight 147 as Chrome gives that priority. There is no Authorization header and no cookie. Discord's cookies are scoped to discord.com, so a browser never sends them to `cdn.discordapp.com` or `media.discordapp.net`, and kyoko's jar stays with the API client.

## Sizes

All sizes are device pixels: points times the display scale, rounded up.

- Avatars, server icons, emoji, banners and role icons use the CDN's `size=`, a power of two from 16 to 4096 (`cdn::bucket`). Avatars and icons are `.webp`; an animated (`a_`) hash adds `animated=true` when the caller wants it animated, otherwise the CDN sends a still. Emoji add `quality=lossless`.
- Attachments go through the media proxy (`proxy_url`, or a `cdn.discordapp.com/attachments` URL rewritten to `media.discordapp.net`). The image is fitted inside the box the caller passes, never upscaled, and asked for as `format=webp&quality=lossless&width=W&height=H`, keeping the signature. GIFs keep their format and only add the size; an attachment flagged animated adds `animated=true`. In a message with several images the box is the one that covers its mosaic tile (`bridge::cover_box`, "Image grid" in `docs/ui.md`), so the proxy returns the crop's source at full sharpness.
- The original-resolution setting (`settings.media.original_resolution`, `cdn::Quality::Original`) fetches the attachment's original `url` with no resize parameters. It replaces Vencord's FixImagesQuality. Memory stays bounded: the decoded image is still shrunk to the box when it is more than twice as large. The lightbox always asks for the original (`bridge::lightbox_request`), with the window as the box.

## Animation

One ticker task sleeps until the next frame of any animating image, then wakes the window, which drains the gallery. An image animates only when it is visible, `Playback` allows it (`Always`; `OnHover` while hovered; never with `Never`) and reduced motion is off. Reduced motion is on when kyoko's `accessibility.reduced_motion` or the system preference is set. Scrolled away, an animation pauses on its frame; when motion is not allowed it returns to its first frame. Finite GIF loop counts are honoured. A frame that is long overdue (the window was busy) restarts the timing rather than racing through the missed frames.

## Server avatars and animated avatars

`bridge::Avatar` picks the picture a person shows in a place: in a server, the member's own avatar (`member.avatar`, from the guild's members, else the server profile's `guild_member`, else the message's `member`) at `<cdn>/guilds/{guild_id}/users/{user_id}/avatars/{hash}`; otherwise the global avatar, else the default one. `MessageEntry.avatar`, `Quote.avatar` and `ProfileCard.avatar` carry it. An `a_` hash is animated; `Avatar::request(.., animate)` adds `animated=true` only when asked, so a still request gets the first frame as a separate image.

Where Discord animates them: message rows and member rows show the still avatar and swap in the animated one while the row is hovered (the timeline's row hover calls `Pictures::hover_avatar`, the member list's Luau row calls `members.avatar_hover`; the hovered name joins the visible set and becomes the gallery's hovered image, so `OnHover` playback plays it too). Popouts, the full profile, the DM profile column, the status menu and the user panel request the animated avatar and banner outright; the media playback setting and reduced motion still decide whether they move. Banners use `ProfileBanner`: the member's server banner (`guild_member_profile.banner`, else `guild_member.banner`) at `<cdn>/guilds/{guild_id}/users/{user_id}/banners/{hash}`, else the global one at `<cdn>/banners/{user_id}/{hash}`.

## GIFs and stickers

What is requested for each kind of moving picture (device-pixel sizes as above):

- GIF attachments: `media.discordapp.net/attachments/…/x.gif?<signature>&width=W&height=H` (the format kept, so the proxy answers with an animated GIF). They used to play only when all their frames fit in the animation share, which a typical 500 by 280 GIF of 40 frames or more does not (on real Discord they showed their first frame); they now stream. An animated WebP or AVIF attachment (attachment flag bit 5) asks `format=webp&quality=lossless&animated=true`.
- GIF embeds (`gifv`, Tenor and Klipy links) carry a `video` (mp4) and a still `thumbnail`. Until inline video (ticket 91) kyoko shows an animated image instead (`bridge::gifv_request`), in this order: a thumbnail or image that is already a GIF or flagged animated is used as is; a Tenor video (`media.tenor.com/<id><code>/<name>.mp4`) becomes Tenor's GIF rendition, `media.tenor.com/<id>AAAAC/<name>.gif` (`bridge::tenor_gif_url`), fetched from Tenor as the web client's GIF picker does; otherwise the video's media-proxy URL asks for an animated WebP, `images-ext-…/external/…/x.mp4?format=webp&quality=lossless&animated=true&width=W&height=H`. Whether the proxy transcodes a video to an animated WebP is not documented (docs.discord.food lists still previews for videos); when it refuses, the request's fallback, the thumbnail through the proxy as any embed image (`format=webp&quality=lossless&width&height`), is shown, so the worst case is the still kyoko showed before. Inline video replaces this in ticket 91.
- Stickers (`sticker_request`, 320 pixels as the web client asks): PNG `cdn.discordapp.com/stickers/<id>.png?size=320`; APNG `cdn.discordapp.com/stickers/<id>.png?size=320&passthrough=true` (the original APNG); GIF `media.discordapp.net/stickers/<id>.gif?size=320` (GIF stickers are not on the CDN); Lottie `cdn.discordapp.com/stickers/<id>.json`, drawn by the Lottie renderer. Before, Lottie stickers drew nothing.

All of these follow the animation settings (`media.gif_autoplay` for GIFs and embeds, `media.sticker_animation` for stickers), reduced motion and visibility, as every animation does. Sticker images in messages report hover, so `OnHover` stickers play under the pointer.

## Expired attachment links

Attachment URLs are signed: `ex` is the expiry in hex seconds, with `is` and `hm`. When a request's `ex` is in the past, the gallery reads the disk cache only and never contacts the CDN. When the CDN answers 403, 404 or 410 for a signed URL, the same applies. In both cases the gallery calls its refresher once with the message's `Origin`, and the desktop sends `Command::RefreshMedia { channel_id, message_id }` to the session. The session queues it on the backfill queue (`docs/rest.md`), which fetches `GET /channels/<c>/messages?around=<m>&limit=1` at its usual pace. `LocalEvent::MediaRefreshed` then replaces the message's attachments and embeds in the channel window and in fetched reply originals. The view re-renders, asks for the fresh URL under the same name, and the image loads. If the fresh URL fails too, the image is marked failed; nothing loops. Stale URLs are never retried, and full signed URLs are never logged (`redact_url` drops the query).

## Audio

Voice messages and audio attachments play through the same pipeline as images: no other network path exists, and the UI thread never fetches or decodes.

- Fetching: `MediaService::audio(url)` reads the disk cache, else fetches with `MediaFetcher::fetch_for(url, Purpose::Audio)`: the same pooled client, host allowlist, redirect checks, 64 MiB cap, per-host queue (at the front, as a user action) and in-flight sharing as images, and the bytes are written to the same disk cache, so a replay reads them from disk. The headers are Chrome's for an `<audio>` element on discord.com (`Fingerprint::audio_headers`): `Accept: */*`, `Accept-Encoding: identity;q=1, *;q=0`, `Range: bytes=0-`, `Sec-Fetch-Dest: audio`, `Sec-Fetch-Mode: no-cors`, `Sec-Fetch-Site: cross-site`, `Referer: https://discord.com/`, the user agent, `sec-ch-ua*` and `Accept-Language`. No Authorization header, no cookie. Image requests keep `Fingerprint::image_headers`; each purpose's headers are set per request. The attachment's `url` is used (its `proxy_url` when it has none). A 403, 404 or 410 on a signed link asks for a fresh one through `Gallery::refresh`, the refresher of expired images; the track shows its error and a new press plays the refreshed link.
- Decoding (`crates/audio`, on the blocking pool): Ogg Opus with the `ogg` demuxer and the pure-Rust `opus-decoder` (pre-skip, end trimming from the last granule, output gain), everything else with Symphonia (Ogg Vorbis, MP3, FLAC, WAV, AAC and MP4/M4A, Matroska). Clips are kept as 16-bit samples, mono or stereo (more channels are folded to stereo), at most 48 Mi samples (`DEFAULT_MAX_SAMPLES`, 96 MiB, about 17 minutes of mono or 8 of stereo at 48 kHz); a longer file fails rather than truncating. The decoders run under `catch_unwind`; a file that does not decode is a failure state, never a panic. Only the playing track's clip is held in memory.
- Playing (`audio::Deck`): one voice at a time, rendered on the output's own thread with a linear resampler to the device rate. 1.5x and 2x keep the pitch (WSOLA: 30 ms Hann windows at 50% overlap, an 8 ms search for the best-matching continuation). Mute sets the gain to 0.
- Outputs (`audio::Sink`): `Device` opens the default output device with cpal only while something plays and closes it on pause; `Silent` is a real-time clock that consumes the samples without sound (mock runs); `Manual` advances only when `AudioPlayer::pump` is called (tests, and the frozen clock of captures).
- `bridge::AudioPlayer` is the controller: `toggle`, `seek(fraction)`, `cycle_speed`, `toggle_mute`, `probe` (reads an audio file's length, through `MediaService::audio`), `left(channel)` and `stop`, and `state(track)` with the phase (idle, loading, playing, paused, failed), position, duration, speed and mute. Starting a track pauses the one that was playing and keeps its place; each track remembers its position and speed until `stop`. The end of a track rewinds it.

## Video

Camera video from other people in a call (v1 103) reaches the window as zgx host images, like pictures, but from the voice connection instead of the gallery. The receive path is in `docs/voice.md`, "Video"; this section is about turning frames into pixels on screen and what that costs.

- `crates/voice` decodes H.264 with the shared decoder in `crates/video` (Media Foundation) on its own `video-decode` thread (NV12 out). There is no other decoder: openh264 stays out of the build (patents, the user's call in v1 96). Without an H.264 decoder MFT (Windows N without the Media Feature Pack) frames are dropped, the desktop's startup probe (`voice::video::available`, on its own thread, so COM never starts on the UI thread) publishes `voice.video_available = false` and camera tiles say "Video unavailable" over the avatar.
- `session::VideoFeed` is the connection's `VideoSink`. For a tile on screen (`Command::SetVideoViews`, below) it converts the decoded frame to RGBA at the tile's size in device pixels (`voice::video::Picture::from_nv12`: nearest sampling, BT.601 limited range through lookup tables, never larger than the source) on the decode thread, and keeps only the newest picture per person until the window drains it. A tile that is not on screen costs a decode but no conversion.
- Frame rate caps: a focused tile shows at most 30 frames a second (`FOCUSED_MAX_FPS`), a thumbnail 15 (`THUMBNAIL_MAX_FPS`); a frame that arrives sooner than three quarters of the gap after the last shown one is skipped, so a 30 fps source shows every second frame and arrival jitter does not drop a thumbnail to 10.
- The desktop (`src/ui/video_surface.rs`) wakes on the feed, drains it and hands each picture to zgx as `host.image("video/<user id>", ImageData)`; the `Arc<[u8]>` moves, nothing is copied. `Clear` (the camera stopped, the call ended) removes the image. zgx gives every `ImageData` a new id, so each frame is a new texture upload, and the previous frame's texture is freed when the node's image changes (zgx-gpu's `node_images`).

### Upload cost (the v1 103 spike)

Measured 2026-10-28 on this machine (Windows 11, 20 logical processors, the dev profile: workspace crates at `opt-level = 1`, dependencies at 3), with other builds running, so each number is the median of three 16-second runs. The source is a 1280x720 30 fps H.264 clip (`ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -t 4 -pix_fmt nv12 -c:v h264_mf -hw_encoding 0 -rate_control quality -quality 40 -g 60 -bf 0 -f h264`, not committed) played by `mockcord --cameras <tiles>:30:<clip>` into the `voice-video` capture screen with the call view open; CPU is the kyoko process's CPU time over wall time, GPU the sum of its `\GPU Engine(pid_*)\Utilization Percentage` counters, and `ZGX_GPU_STATS=1` gave the frame and texture figures (tile sizes from the resident texture bytes; the window was 1920x1200 at 150%).

| Call view | CPU (one core = 100%) | GPU engines | Shown |
|---|---|---|---|
| no video (baseline) | 3.4% | 0% | |
| 1 tile, shipped caps (thumbnail, about 630x354 px, 15 fps) | 28.5% | 2.4% | 15 fps, 13 MB/s of RGBA |
| 4 tiles, shipped caps (thumbnails, about 525x295 px each, 15 fps) | 66% | 4.2% | 60 pictures/s, 37 MB/s |
| 1 tile, uncapped (native 1280x720 RGBA, 30 fps) | 79% | 4.2% | 30 fps, 110 MB/s |
| 4 tiles, uncapped | 184% | 5.9% | 120 pictures/s, 442 MB/s |

Per stage (`cargo run -p kyoko-voice --example video_cost -- <clip> <mode>`, CPU time of the process):

- Media Foundation decode of a 720p frame: 6.6 ms of CPU (3.7 ms of wall time; the software MFT uses several threads), so about 20% of a core per 720p30 stream, whatever the tile size. Every frame must be decoded.
- NV12 to RGBA: 5.3 ms at 1280x720, 2.7 ms at 942x530, 0.9 ms at 470x264 (one thread; 17 ms at 720p before the lookup tables).
- The zgx upload is the rest: about 8 to 10 ms of CPU per 720p frame on the render thread (the straight-alpha premultiply in `upload_image` and a fresh texture each frame), against well under a millisecond of GPU time. Uploading full 720p frames at 30 fps is what makes the uncapped rows expensive, so the caps stay: pictures at tile size, thumbnails at 15 fps.

Findings for later tickets: decode dominates once the pictures are small, and on Discord a thumbnail's wants of 50 make the SFU send the lower simulcast layer, which cuts it further (mockcord always sends the full clip). Hardware decode (Media Foundation with a D3D11 device manager) and a zgx surface that takes NV12 textures (zgx has no Windows native surface; `NativeSurface` is macOS only) would remove most of the remaining cost; neither is needed for 4 tiles.
