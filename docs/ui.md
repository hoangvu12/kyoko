# Interface

Kyoko's interface is a 1:1 port of oxidcord 0.2.0-beta.1, written in Luau on zgx. The Rust host in `apps/desktop/src/` owns the window, the theme and everything that touches the session. The Luau scripts in `apps/desktop/ui/` lay out and draw. This page is the pattern every UI ticket follows. `docs/parity.md` says how a screen is compared with oxidcord.

## Where things live

```
apps/desktop/src/
  ui.rs            the window: Link (session to Luau), host actions, shared values, the Rust root layout
  theme.rs         palettes to zgx themes, installing and switching them
  fonts.rs         the bundled Inter faces, installed font families, picking the first of a font list
  frame.rs         the native window: maximized state, the exit waker
  timeline/        the message timeline, a Rust view in the timeline slot (below)
apps/desktop/ui/
  .luaurc          strict mode; aliases @components and @shell
  app.luau         the entry: requires the shell and returns its root
  theme.luau       every theme token by name, as zgx token strings
  state.luau       every shared value the host publishes, typed, in one place
  actions.luau     every host action and function the scripts call
  components/      reusable pieces with no screen of their own (icon, icon_button)
  shell/           one module per region of the window
  icons/           oxidcord's icon set, one SVG per icon name
```

A screen or component is one module that returns a function building its node. Use `ui.component` only when the piece needs per-instance state (`ui.use_state`), as `components/icon_button.luau` does for hover. Modules require what they use: `require("../theme")`, `require("../state")`, `require("../actions")`, `require("@components/icon")`. In debug builds the host reloads the scripts when a file changes, so Luau work needs no rebuild. Rebuild Rust only for host changes.

### The load check

`cargo xtask test` and `cargo test --workspace` check the scripts headless, with no window and no network, in under a second once built (`src/ui/scripts.rs`). Run it alone with `cargo test -p kyoko --bin kyoko ui::scripts`.

- `every_script_compiles`: every `.luau` under `ui/` must parse. A syntax error fails with the file and line (`actions.luau:6: Expected 'end' ...`).
- `the_interface_loads_and_builds_every_screen`: `app.luau` loads in zgx's `testing::TestApp` with the real theme installed and a stub action and function for every `"area.name"` string literal in `src/`, then builds the terms notice, the token form, the DMs, a server with its channels and members, every settings page, and a home page from sample shared values. Each screen must show its marker text. A missing `require`, an unregistered host name or a runtime error fails it with the script's traceback and the screen it was building.
- `the_typing_dots_animate_only_while_the_setting_allows`: reads the opacity of the composer's `typing_dot_*` nodes over real time and checks they cycle with `chat.typing_animation` on and stay lit with it off.

To stay loadable, a new module must:

1. Parse, and require only modules that exist (`./`, `../`, `@components/`, `@shell/`).
2. Call the host only through names Rust registers with a string literal (`host.action("area.name", ...)`, or a literal list it loops over); a name built at runtime is not stubbed.
3. Build without error when every shared value is at its `state.luau` default, since the check starts from those.
4. If it is a new screen or region, get sample shared values and a marker text in `scripts.rs`, so the check builds it too.

## Shell regions

`shell/frame.luau` lays the window out as Midnight's floating panels (Midnight 03, `docs/design/midnight.md`): the window is `bg_3`, and every region is a `components/panel.luau` (`bg_4`, `radius_lg` corners, a `border_thickness` border in `border`, clipped), `gap` apart and inset `gap` from the left, right and bottom. Sizes are Midnight tokens only; values that are sums of others are derived tokens (`DERIVED_SIZES`), never arithmetic in Luau.

The window controls sit outside every panel tree, in the root column, so they show on the login screen, over settings and over home pages alike; the channel header keeps an empty box of `window_controls_width` at its right end so they land inside it, as the mockups have them. The help button is left out: Midnight hides it in titlebar mode. Home pages (`home_page.luau`, M21) cover the page column with their own panels on `bg_3`: a header panel (`channel_header_height`, keeping the `window_controls_width` box) over the page's content panel and, for Friends, the Active Now panel (`friends_active_width` 360). In zgx an absolute node's `top`, `left` and `right` take numbers, so pass `theme.number(theme.size.x)` there, not the token string, and give an absolute node pinned by `right` an explicit width.

Motion: list rows slide on hover through `motion.slide(hovered, rest, shift)` (`@components/motion`): channel rows and Friends/Nitro/Shop by `list_item_hover_shift`, DM and member rows by `member_hover_shift`, over 200 ms. The channel unread marker is an `unread_dot_size` dot centred on the panel's left edge (half clipped) that slides in with its row. The home mark spins -360 degrees and shrinks to 0.8 over 400 ms while hovered. Under reduced motion (`accessibility.reduced_motion` or the system's) none of these move (`motion.moving`); `hover_slides_and_the_home_spin_stay_still_under_reduced_motion` checks it headless.

The login screen (`login.luau`, tickets 21 and 44 and Midnight 24: the card, the email and token forms, the two-factor step, the captcha hand-over, the unsaved token and the notice; its QR column `login_qr.luau`, ticket 42, and the web login window `login_web.luau`, ticket 43; all on Midnight tokens) stands beside the shell: `frame.luau` shows it instead of the shell while `login.screen` is not `main`, with the same title bar. `storage_notice.luau` is a warning bar under the title bar, shown only when `session.storage_warning` is set. The web login window is a Luau overlay inside the login screen, so the window controls stay above its scrim; the page itself is a WebView2 child window that the Rust side places over the `web_login` slot (`frame.slot`). It is not a root overlay layer, being a native window rather than a zgx view. Since v1 68 the card leads with "Sign in on discord.com" beside the QR column, and the email form is one link away (`login.mode`: `discord`, the default, `email` or `token`): native password login is where other third-party clients' users meet captchas and disabled accounts, so kyoko steers people to Discord's own page or the phone. This departs from `login.html` and `login-email.html` on purpose; tokens, spacing and type still follow them. See `docs/sign-in.md`.

Overlays (menus, popovers, dialogs, toasts, the lightbox, settings) are added beside the shell's root by the tickets that build them (28, 30–38).

### The timeline slot

zgx cannot place a Rust view inside a Luau tree, so the Rust root layout in `ui.rs` is an overlay: the Luau view fills the window, and a Rust view is absolutely positioned above it at the box the Luau timeline reports. The Luau box is inset `space_6` from the chat panel's top and `space_4` from its sides, which keeps the rectangular Rust view inside the panel's rounded corners and border. `shell/timeline.luau` is an empty box that calls `actions.report_slot("timeline", element)` from `on_resize`. The host function `frame.slot` turns that into the `Slot` signal `timeline_slot` follows, and tells the timeline its size. Because the Rust view sits above the whole Luau tree, a Luau overlay (menu, popover, dialog, lightbox) that covers the timeline's box is drawn under it: a ticket adding one either draws it in Rust above the slot or hides the slot while it is open. A Luau `ui.modal` is the exception: zgx raises an open modal to the top of the window's root, above every Rust layer, which is how settings (Midnight 19) draw over the live timeline.

### Root overlay layers

Every Rust layer above the Luau tree (the slots, the modal scrim, profiles, the quick switcher, thread popouts and dialogs, community dialogs, the expression picker, the lightbox, the moderation dialogs and member menu, the composer's menu, attachment dialog and drop card, friend confirmations, the apps launcher, the inbox) is one entry in the `layered(host.view(), [...])` list in `ui.rs`. `layered` puts each entry in a zero-size absolute box at the window's top left, so a layer never takes layout size from the overlay. This matters because zgx hit-tests by box: a press goes to the topmost node whose box contains it, containers included, then to that node's nearest ancestor with listeners. A layer stretched to the window (as any plain `div()` child of `overlay()` is) therefore sends every press to the root overlay's own listeners, and the Luau tree and the timeline beneath never see it. Ticket 31's switcher, a plain `div()` around its modal, did exactly that until 61.

To add a layer: append its view to the `layered` list, and to `LAYERS` in `src/ui/root.rs`. Its root sizes itself explicitly, to the window (`w(width).h(height)` from a window signal) only while something is open and 0 by 0 otherwise; zgx's `modal`, `popover` and `menu` are portals and need no size. Never attach listeners to a node that covers the window while the layer is closed. `ui::root::presses_reach_the_luau_tree_through_every_closed_layer` builds the root overlay around the real Luau shell with each closed layer, presses the top bar's threads, pins and inbox buttons, and fails naming the layer that swallowed them; `cargo xtask test` runs it beside the load check.

## The timeline

`src/timeline/` is the message list. `bridge::Timeline` projects the open channel's `State::channel_rows` into keyed rows (`RowKey`: `Loading`, `Start`, `Day(date)`, `Unread`, `Message(id)`, `Pending(nonce)`) and publishes what changed since the last publish as a `bridge::Delta`: `reset` (a channel switch or a wholesale reload), `prepended` and `appended` counts, and `inserted`, `updated` and `removed` keys. `Link` hands the rows and the delta to `TimelineView::apply`; nothing goes through a shared value.

- Rows: zgx's `measured_virtual_list` over the keys. Heights are kept by key across inserts and removals, rows not yet mounted take an estimate from their text (`rows::estimate`), and mounted rows are measured. Each key has a signal holding its `Row`, so an edit restyles one row. `rows::render` has one renderer per row kind (skeleton, welcome, day separator, unread marker, first message of a group, follow-up, system message); ticket 26 extends the message body there.
- Follow: `VariableHeights::anchor_end` keeps a viewport resting at the end there when rows are added or measured. A channel switch scrolls to the end.
- Anchoring: when the rows change and the reader is not at the bottom, the view remembers the first visible rows by key and their distance from the viewport top, and after the change sets the offset so the first of them that survived sits exactly where it was. zgx re-anchors only point height changes, so this covers prepends, inserts and removals above (`scroll::Anchor`).
- Paging: within 14 rows of the top (or with fewer than 14 rows), while the channel has older history, the view sends `LoadOlder`; while the window is detached and the reader is at the bottom it sends `LoadNewer`. Each is sent once per edge message, again after 3 seconds (`scroll::Paging`); the session also drops a duplicate in-flight page.
- Viewport: the first and last visible message ids and whether the reader is at the bottom (within 2 points) go to the session as `SetViewport`, at most once per 250 ms and only when they change (`scroll::Reporter`). The session decides acks from it; the timeline never acks.
- Images: `timeline::Pictures` is every image the rows show, through the gallery: avatars (`Circle`, 40 points; 16 in reply previews), custom emoji (22, 48 when jumbo, 16 in reactions), attachments fitted to 550 by 350, embed images (400 by 300, thumbnails 80, author icons 24), stickers (160). `Pictures::names_in` lists an entry's images the same way the rows request them, so the images of the visible rows (and two rows either side) are merged with the user panel's avatar, the rail icons and the Luau `media.visible` set into one `Gallery::set_visible` call: animated emoji, GIFs and animated WebP play only on screen, as the gallery's playback and reduced-motion settings allow. In mock runs every URL that is not the mock server's goes to its `/media/<hash of the path>.png`, as oxidcord's mock resolver does, and the mock fetcher refuses remote hosts. Attachments and embeds show their thumbhash placeholder until the image arrives.
- Text in the list is selectable and copies with Ctrl+C (`selectable`); one selection runs across a message's paragraphs and copies plain text, mentions as their names, Unicode emoji as their characters and custom emoji as `<:name:id>` (`<a:name:id>` when animated). Timestamps are local time, formatted as oxidcord does (`bridge::message_time`, `clock_text`, `day_label`, `timestamp_text` for `<t:..>`); a relative `<t:..:R>` rounds to the nearest unit, as Discord's does.
- Plugin formatting: author names (`MessageEntry::author`, with `author_extra` drawn after it in `text_muted`) and relative times (`Display::timestamp`, read from `RowEnv::display` in `body.rs`) go through `bridge::Display`, the cache in front of the display hooks; the member list and profiles use it too ("Display hooks" in `docs/plugins.md`). Nothing calls a plugin while drawing: a cache miss draws kyoko's own text and the answer redraws the row.

### Message content

`bridge::Timeline` lowers each message once into its `MessageEntry`: `body` (the markdown of the content, embed descriptions and field values, parsed once per message revision and cached), `names` (every user, role and channel mentioned, resolved through state; an unresolved user reads `@unknown-user` until the session fetches it), `reply` (`ReplyPreview::{Message, Deleted, Unavailable, Loading}` from `State::reply_target`; `Loading` without Read Message History reads as unavailable) and `system` (the line and icon of a system message). A resolved mention or reply changes the entry, so only that row redraws.

The row renderers are in `src/timeline/`: `rows.rs` (the frame of each row kind, reply previews, system rows with oxidcord's icons, deleted styling: muted text with a red `(deleted)`), `kept.rs` (what a plugin's `MessageLook` changes: the deleted style, red text or a `background_feedback_critical` tint, earlier versions drawn dimmed above the text, a clickable `(edited)` that opens a collapsed history, and accessory lines under the message; see "Message looks" in `docs/plugins.md`), `body.rs` (markdown: one zgx `rich_text` paragraph per run of inline content, blocks for headings, subtext, quotes, lists and code), `inline.rs` (emoji: a padded placeholder in the paragraph, with the image laid over its shaped rectangle after layout, so wrapping and selection stay one paragraph; see "Emoji" in `docs/emoji.md`), `attachments.rs` (images, file and video cards, embeds, stickers, Lottie ones through the media crate's Lottie renderer), `extras.rs` (polls, thread chips), `reactions.rs` (reaction chips, their tooltip, the Reactions list) and `links.rs`. Code blocks are highlighted by the `markdown` crate's own highlighter. Unicode emoji are drawn from the bundled Twemoji set through the same placeholder as custom emoji (`docs/emoji.md`); inline code keeps them as text.

Interactions owned here: spoilers reveal on click (per message, kept while the window lives), poll answers vote (`VotePoll`; a multi-select poll collects picks and sends them with Vote; the author can End Poll), embed titles, author links and video embeds open their links, file cards open the file. A link opens at once for oxidcord's trusted hosts and the user's `trusted_link_hosts`; any other host first shows the "Leave Kyoko?" dialog (a zgx modal from the timeline view, so it sits above the slot), whose "Always trust" saves the host to settings. Opening goes through zgx's `open_url`. Image attachments and bare image embeds open the lightbox (below); profiles are below too.

### Message actions

`bridge::message_menu` decides which actions a message offers, in Discord's order (Midnight 07, `message-menu.html`, `message-menu-own.html`) with kyoko's actions only: Add Reaction, View Reactions (when the message has any); then Edit Message (own), Reply, Forward, Create Thread; then Copy Text, Pin or Unpin Message (Manage Messages, or any DM), Mark Unread, Copy Message Link; then Select or Deselect Message (own messages, or Manage Messages), Delete N Selected, Delete Message (own, or Manage Messages) and Report Message (others'); then Copy Message ID (developer mode). A separator sits between the groups. It reads a `bridge::Access` (the open channel's permissions and safety lock), which `Link` hands the timeline on every publish. `bridge::toolbar_actions` gives the hover bar (Add Reaction, Reply, Edit). System, pending and deleted messages get no actions; a kept deleted message only copies. Links are `https://discord.com/channels/<guild or @me>/<channel>/<message>`.

`src/timeline/actions.rs` draws them, all from Rust in the timeline view, so they sit above the slot (the overlay rule):

- The context menu opens on a right click as a zgx `menu` anchored at the pointer, in Midnight's menu look (`kit::menu_panel`, `kit::menu_row`): `menu_width` 220, `bg_3`, a `border_thickness` `border`, `radius_sm`, items `menu_item_height` 32 inset 8, the label (14 medium `text_3`) left and a 16-point `text_4` icon right, the neutral `hover` wash on hover (zgx's `menu.hover`, `#373534` on `#31302f`), danger items in `red_2` on `background_feedback_critical`, separators 1 point with 4 around them. Copy Message ID shows an ID badge. Above the items, the quick reactions: up to four of the user's frequently used emoji (`PickerSection::Recent`), each on a `bg_4` tile, which toggle that reaction; they show only in the open channel when Add Reaction is allowed. Item ids are `message-menu-<label>` and `message-menu-react-<key>`. zgx keeps popups inside the screen, so the anchor is moved up and left first to keep the menu inside the window, as oxidcord's does. zgx draws menus, popovers and tooltips in separate popup windows on Windows; the parity capture composites them (`docs/parity.md`).
- The hover bar shows on the row under the pointer (and while its More menu is open, or while the reaction picker opened from it is open, as Discord keeps it; hidden while its context menu is open): Add Reaction, Reply, Edit and More, which opens the same menu.
- Delete, Delete N Selected, Pin and Unpin confirm in a Midnight dialog (`dialogs.rs`, `delete-message-dialog.html`): Delete Message and Pin show the message (avatar, author, time, text) on `bg_3`, Delete adds Discord's protip, and the footer has Cancel and Delete (`red_3`) or Pin (`accent_3`). Shift while choosing Delete Message skips the confirmation, as the web client does.
- Selecting: Shift-click a message, or click one while any is selected, or use Select Message. Selected rows take `message_selected`. A bar at the bottom shows the count with Cancel and Delete; Delete confirms and sends `DeleteMessages` (paced single deletes, never bulk delete), and the bar then follows the batch from `State::deletions()`: "Deleting 2 of 3…", then what was deleted, refused and why the rest stopped. Escape clears the selection.
- Alt-click a message marks it unread (`MarkUnread`).
- Reactions: a reaction chip toggles your reaction; Add Reaction opens the emoji picker (`src/pickers/`, oxidcord's emoji tab: search, a rail of recent, server and Unicode sections, a preview footer and skin tones; Enter in the search picks the first result) as a popover beside the pointer. A new emoji needs Add Reactions, joining an existing one only Read Message History. When the channel has a safety lock the reaction is held and the bar shows the lock's explanation with "React anyway", which sends `ConfirmRisky` then the reaction; for a gate it only explains.
- Reaction chips (Midnight 06, `reactions.html`; `timeline/reactions.rs`): `bridge::reaction_chips` gives one chip per reaction and kind, a super chip (from `count_details.burst`) before the normal one of the same emoji. A chip is `reaction_height` 24, a `reaction_border_width` 2 border, `radius_sm`, 6 in, a 16-point emoji and the count (14 semibold): `hover` with a `border_light` border (`active` and `bg_2` hovered); yours `reaction_background_reacted` with an `accent_2` border and `text_1`. A super chip draws its border as a gradient (the reaction's `burst_colors`, first to last; `purple_2` to `blue_2` without them, Midnight's `--super-reaction-border`) around `bg_4`, adds a 12-point `purple_2` sparkle after the count, and when it is yours fills with the same gradient at 20%. Clicking a chip toggles that kind (`AddReaction`/`RemoveReaction` with `burst`). On a hovered row, Add Reaction and, only for an account with Nitro, Add Super Reaction follow the last chip; both open the emoji picker, the second sending super reactions. kyoko never shows an upsell.
- The chip's tooltip (`reaction_tooltip_width` 300, `bg_3`, 1-point `border`, `radius_sm`, 8 above the chip at its left edge) shows the emoji at 32 and "hungry, edelweiß and 2 others reacted with **:thumbsup:**" (`bridge::reaction_tip`: everyone up to three, otherwise two and "N others"; "super reacted with" for a super chip; the count alone until the names load). Hovering a chip asks for its first page of reactors once (`LoadReactionUsers`). zgx's tooltip has no pointer arrow.
- The Reactions list (`reactions-list.html`) opens from View Reactions: a `kit::dialog` 440 by `reactions_list_height` 400 over the scrim, with Reactions and Super Reactions tabs (the second only when there are super reactions, and listing only them), a 120-wide column of reactions (32 high; `active` when selected; a sparkle on super ones) and who reacted: 44-high rows with a 32-point avatar, the display name and the username, in a virtual list that asks for the next page when its last row comes into view. With Manage Messages a hovered row other than your own shows a remove button (`RemoveUserReaction`). Ids: `reactions-list`, `reactions-tab-all`, `reactions-tab-super`, `reactions-column-<normal|super>-<key>`, `reactor-<user>`, `reactor-remove-<user>`, chips `reaction-<message>-<normal|super>-<key>`, `reaction-add-<message>`, `reaction-add-super-<message>`.
- The reaction picker saves favourites the same way the composer's picker does (`SetEmojiFavorite`).
- Failures the session reports (`CommandRejected`, such as a refused pin or reaction) show in the same bar for a while after the user acted.
- Reply and Edit hand the message to the composer (`Compose::Reply`, `Compose::Edit`, through `Link::composer_reply` and `Link::composer_edit`). Clicking a reply preview jumps to the original: `TimelineView::jump_to` scrolls to it when it is loaded, otherwise sends `LoadAround` and scrolls once the reset arrives. Clicking an avatar, an author name or a user mention calls the profile hook (`TimelineView::on_profile`), which opens the profile popout at the pointer.
- Create Thread opens the Create Thread dialog ("Threads and forums" below). Forward opens the forward dialog ("Community dialogs" below); Report Message opens Discord's report page, as oxidcord does.
- Plugin items (`message.menu`, "Menu items" in `docs/plugins.md`) follow kyoko's own after a separator, from `crate::plugin_menu::PluginMenu`, which `Link` fills from `PluginHost::menu_items` on every host change and shares with the thread pane and the pickers. An inline custom emoji, a reaction chip or a sticker marks itself on a secondary press (`timeline::actions::aimed`), so the row's right click knows what was under the pointer and the conditions see it; the hover bar's More menu and search results have no target. Choosing an item records the press (the gesture rule) and runs `PluginHost::menu_gesture` on a blocking thread (`src/ui/cloner.rs`).

### Midnight timeline (M05)

The rows are Midnight's (`docs/design/midnight.md`, Chat panel), drawn in `rows.rs`, `body.rs` and `attachments.rs`:

- Each message row sits 0 points from the slot's left and 8 from its right, which with the slot's own 4-point inset gives Midnight's 4 left and 12 right inside the chat panel. Rows have `radius_md` corners, `message_hover` when hovered and `message_selected` when selected. Content starts at 72 (`message_content_left`), groups are 17 apart (`message_group_gap`), authors are 16 medium in `text_2` (or the role colour), timestamps 12 medium `text_5`, follow-up times 11 `text_5` right-aligned in the first 56 points, body text `text_3`.
- Highlights come from `MessageEntry::highlight` (`bridge::Highlight`): `Mention` when the message mentions you (`State::mentions_me`: you, `@everyone` unless suppressed, or one of your roles), `ReplyToYou` when it replies to your message. The background is Midnight's gradient, the token colour from 0 to 40% of the width fading to transparent (`mention`/`mention_hover`, `reply`/`reply_hover`, read through zgx's `Themes` so it follows a theme switch), with a 4-point bar (`accent_2`, `text_2`) 4 in from the left and 8 from the top and bottom. A MessageLogger tint (`kept::tinted`) wins over both.
- Reply previews are 18 high with a 2-point `text_5` spine; the bot tag is `accent_2` on `text_0`. Deleted text is `text_5` with a `red_2` "(deleted)", edited messages end with "(edited)" in `text_5` (`kept.rs`).
- The unread divider is a 10-point row: 6 down, a 4-point `accent_new` line from 12 to 10 inside the slot and the NEW pill at its end. The message after it always starts a new group (`state::rows`).
- Code blocks: `bg_3`, a `border` border, `radius_md`, 7 padding, at most 90% wide, 14/18 `text_3`; inline code on `bg_3`. Embeds: 432 wide at most, `bg_3`, `radius_md`, a 1-point `border` and a 4-point bar in the embed colour (`border` without one), 16 padding, the large image 12 under the text. File cards are `bg_3` with a `border` border.
- The hover bar floats 16 above the row's top, 12 from its right: `bg_3`, `border`, `radius_sm`, 32-point buttons with 20-point `text_4` icons (`text_2` and `hover` when hovered). On your own message with embeds that are not suppressed it starts with Remove all embeds (`bridge::can_remove_embeds`), which sends `Command::SuppressEmbeds`.

New messages bar (`timeline/unread.rs`): while the open channel has an unread marker, a bar floats 6 under the slot's top and 8 in from its sides (12 inside the chat panel): `accent_3`, `radius_sm`, 32 high, 14 medium `text_0`, "N new messages since 5:11 PM" (with the date when not today, "N+" while newer history is not loaded) and "Mark As Read" with its icon. The text jumps to the divider; Mark As Read sends `MarkChannelRead`. It goes when the marker does.

GIFs: a `gifv` embed (Klipy, Tenor) is an animated image standing in for its video (`Pictures::bare_embed`, `bridge::gifv_request`; see "GIFs and stickers" in `docs/media.md`), fitted to 400 by 300 (`pictures::bare_box`), and so is a GIF attachment; a message that is only that link hides its text (`pictures::only_link`). Hovering one plays it (the gallery's hover) and shows the favourite star, 28 points at 6 from the top right on `overlay_button_background`, filled when the GIF is a favourite (`RowEnv::favorite_gifs`, from `State::favorite_gifs`). The star sends `Command::SetGifFavorite` with `bridge::favorite_gif` / `favorite_gif_attachment`; the first hover asks `LoadFavorites` once. ## Theme

`crates/bridge/src/themes/tokens.rs` holds every token in one place: `COLORS` and `SIZES` with the dark defaults, the `light` and `amoled` overrides, the `MIDNIGHT` palette, the derivations (`DERIVED_COLORS`, `DERIVED_SIZES`), and the UI and code font lists. Two sets of tokens live there side by side: oxidcord's, which every screen not yet restyled uses, and Midnight's (below), which the Midnight restyle tickets move each screen onto. `bridge::themes::Palette` is a whole theme and `Layer` a set of overrides on top of one (`docs/themes.md`). `bridge::themes::Themes` loads the built-in themes and every `themes/<id>/theme.json` beside the source (or `KYOKO_THEMES_DIR`) as bases, and the user's themes folder and theme links as layers, and gives each base with the enabled layers applied. `apps/desktop/src/theme.rs` turns palettes into zgx themes (`to_theme`, with the zgx standard token mapping): `Catalog::install` registers them and applies `settings.theme` (`midnight` by default; `system` follows the system's light or dark), `Catalog::apply` switches the base, and `Catalog::replace` re-registers the palettes a layer changed, so the window restyles at once.

Every token is the zgx app token `kyoko.<name>`: `kyoko.background_primary`, `kyoko.radius_md`, `kyoko.ui_font`. zgx's standard tokens are mapped from them too (`background`, `text.primary`, `accent`, `font.sans`, `font.mono`, scrollbars, hover washes), so zgx's own widgets, scrollbars and menus match the theme.

Luau reads tokens only through `theme.luau`, never as literal colours:

```lua
local theme = require("../theme")
ui.row { h = theme.size.top_bar_height, bg = theme.color.background_primary,
	ui.text { "general", text_size = theme.size.font_md, weight = theme.weight.semibold, color = theme.color.header_primary } }
```

`theme.color.*` and `theme.size.*` are token strings, so a theme switch restyles without running the script. A property that only takes a number (such as `rounded_tl`) uses `theme.number(theme.size.radius_md)`. A new token goes into `COLORS` or `SIZES` (`crates/bridge/src/themes/tokens.rs`) and into `theme.luau` together. The only literal colour allowed is a fully transparent `#00000000` to clear a control's own background.

### Opening a server

Discord's web client never shows a server with an empty message area. Opening a server reopens the channel last viewed in it, and a server never visited opens its default channel. kyoko does the same (ticket 80):

- `Link::visit_guild` selects the server, then opens `bridge::landing_channel`. Clicking a server on the rail (`rail.select_guild`), picking one in the quick switcher and arriving in a newly joined server all go through it. Clicking the server that is already open leaves its channel alone. Paths that open a specific channel (`Link::open`, a thread, a forum, a capture's `Opening`) select the server without landing, so one channel open still sends one history page.
- At launch, and whenever the selected server changes on its own (the first server picked once the guild list arrives, or the open server deleted or left), `Link::follow_selection` lands the same way.
- `bridge::landing_channel` returns the last viewed channel when it can still be reopened. That means it is still in the server's channel tree (an active thread counts), the user can view it, and it is a text, announcement, voice, stage, thread or forum channel. Otherwise it returns the default channel: the first text or announcement channel the user can view, in sidebar order (categories by position, channels by position within them, uncategorised channels first). This is the same rule as `bridge::replacement_channel`. A deleted channel, a channel that lost View Channel, an archived thread and a channel in a server with no readable text channels all fall back. If nothing can be opened, the area stays empty.
- Memory: the session records the server and channel of every `Command::SelectChannel` that carries a `guild_id` (`State::last_channel`, `LocalEvent::ChannelSelected`). DMs are not recorded. When the pair changes, the session writes all the pairs to kv `navigation.last_channels` (a JSON list of `[guild_id, channel_id]` string pairs, servers the user has left dropped). It loads them before the cached READY at launch. Each account has its own database, so the memory is per account, and sign-out wipes it with the rest of the account data. Entries that don't decode are skipped one by one.

The web client keeps this navigation memory on the device, not on Discord's servers. The user settings proto (`PreloadedUserSettings`, `GuildSettings`, `ChannelSettings`) has no last-viewed or selected-channel field: [docs.discord.food, User Settings Proto](https://docs.discord.food/resources/user-settings-proto). The only per-server progress it stores is the onboarding notice and hub flags. kyoko therefore saves it locally and syncs nothing. Discord points onboarding members to the server guide (`GUILD_SERVER_GUIDE`, "new member welcome", [docs.discord.food, Guild](https://docs.discord.food/resources/guild)). kyoko has no server guide view, so a community server also opens its first readable text channel. The rules channel (`rules_channel_id`) is not a default either.

### Live markdown in the field

Discord draws markdown inside the composer itself. zgx's editable field holds plain text with one style (`TextEditor` laid out as plain text runs), so kyoko uses only flat backgrounds behind byte ranges (`decorations`, line-box rects with square corners). zgx's per-line colour (`highlight`, the code-editor highlighter) was tried for the dimmed markers and left out: once it is set the editor lays the text out a line at a time and, in a wrapped field, paints lines wrapped wider than its own caret layout (the caret sat lines below the text), draws nothing for a very long single line (about 4,000 characters), and drops the placeholder. Drawing the rest needs zgx to grow, in its editor:

- a highlighter whose line layout matches the editor's wrapped layout (caret, long lines, placeholder);

- per-range text attributes fed into the editor's own layout (weight, italic, family, size, colour), so carets, hit tests, selection and IME follow the styled metrics;
- padding and corner radius on range backgrounds, and a line decoration for the quote bar;
- atomic inline objects: a sized box (an image or SVG, a chip with a label) drawn over a byte range that stays raw text in the value, which the caret and Backspace treat as one unit;
- the same on single-line inputs, and all of it on `ui.textarea` in Luau.

## Quick switcher

Ctrl+K anywhere in the window (and the DM sidebar's "Find or start a conversation" bar, `dms.search`) opens the quick switcher. It is a zgx modal drawn in Rust from a layer of the root `overlay()` in `ui.rs`, so it sits above the timeline slot (the overlay rule): `src/switcher.rs`, in Midnight's look (M22, `quick-switcher.html`): `modal_width_md` wide, 180 from the top, `bg_4`, `radius_lg`, a `border` border, 24 padding (16 at the bottom); the "Where would you like to go?" field (`switcher_input_height` 70, `bg_3`, an `accent_2` border, 24-point `text_2` text), the list (12 bold uppercase `text_4` group headers; `switcher_row_height` 34 rows with `radius_xs`, a 20-point icon or avatar, the name 16 medium `text_3`, the server or username 12 semibold uppercase `text_4` at the right; the selected row `active` with `text_2` and a ↵ key badge) and the PROTIP footer (`green_2` lead) under a `border` line. Escape or a click on the backdrop closes it; Ctrl+K again toggles it.

- The model is `bridge::QuickSwitcher` (`crates/bridge/src/switcher.rs`), built from `State` on every open by `switcher_entries`: every readable channel, forum and active thread of every server (locked channels left out), voice and stage channels as their own group, DMs and groups, friends without a DM yet, and servers. - `bridge::RecentTargets` keeps the last 8 opened channels or DMs; `Link::publish_timeline` remembers each one as it opens.
- Up and Down move the selection (it wraps), Enter or a click opens: a channel through `Link::open`, a DM through `select_dm`, a server through `select_guild` (as the rail does), a friend through their DM or `Command::OpenDm`, which the session's DM lock guards.
- Avatars and server icons are 24-point gallery images from the timeline's `Pictures`, part of `Gallery::set_visible` while the switcher is open.

## Message search

Enter in the channel header's search field (`search.run`, `search_width` 240) parses the text with `bridge::parse_search` and sends `Command::Search` for the open server, or for the open DM with `channel_id`.

- Filters, as the web client's: `from:` and `mentions:` (a name, username, `@name` or `<@id>`, resolved among the server's cached members or the DM's recipients), `has:` (`image`, `video`, `sound`, `file`, `sticker`, `embed`, `link`, `poll`; repeatable), `before:`, `after:` and `during:` (`YYYY-MM-DD`, turned into snowflake bounds), `in:` (a channel of the server, by name or `<#id>`) and `pinned:true|false`. A filter whose value does not resolve stays in the text. Each applied filter shows as a chip under the header.
- The session paces it ("Message search" in `docs/rest.md`); results arrive as `Session::search_results()` with `Changes::search`.
- `shell/search_panel.luau` is Midnight's results panel (M22, `search-results.html`): a `search_results_width` 420 column in place of the member list while `search.panel.open` (from 900 points wide). The header holds "N Results" or "Searching...", the sort (`search.sort`: Newest, or Oldest, which sends `SearchQuery::oldest_first`, `sort_by=timestamp&sort_order=asc`), the close button (`search.close`, which sends `Command::CloseSearch`), the Messages, Media, Links, Files and Pins tabs (`search.tab`, `search_tab_height` 28, the chosen one `active`; they run the same text again with `has:image`, `has:link`, `has:file` or `pinned:true` added) and the chips. Then a notice line while Discord is indexing or after a refusal, and the hits grouped by channel (a channel icon and name over each run of hits from one channel), each a `bg_3` card with a `border` border (`border_light` hovered), the 40-point avatar at 12/8, the author 16 medium `text_2`, the time 12 `text_5`, a four-line snippet with the searched words marked in `accent_3` (`bridge::marked_runs` over `bridge::search_terms`, as `ui.rich` spans) and a Jump button on hover. The footer pages through them, 25 to a page (`bridge::RESULTS_PAGE`, `search.page`): a back arrow, up to five page numbers (the current one `accent_3`) and a next arrow; a page past what is loaded asks for more with `Command::SearchMore`.
- `bridge::SearchPanel` lowers each hit with `bridge::detached_entry` into the same `MessageEntry` the timeline uses (names, colours and body through state), taking the server from the search scope when the payload has no `guild_id`.
- A click (`search.open_result`) opens the hit in context: its channel or thread opens if it is not the open one, then `TimelineView::jump_to` scrolls to it or loads around it.
- Right-clicking a card (`search.menu`, with the window position) opens the timeline's own context menu (`MessageActions::open_menu_at`) with the hit's channel `Access`, so the items, their order and their gating are exactly the timeline's (FullSearchContext). Actions that need the channel open (Add Reaction, Reply, Edit, Select, Deselect, Delete Selected) first open the hit in context, then run once its row is loaded (`TimelineView::jump_then`); the others (copy, pin, mark unread, delete, report) act at once. Selection counts only for the open channel.

## Community dialogs

## Toasts, transitions and connection status

Toasts are oxidcord's in-window notices (gpui-component's notifications), not the Windows toasts of `docs/desktop.md`. `bridge::Toasts` is the queue: `push(kind, text, now)` (Info, Success, Warning, Error; the same text again only restarts its timer), five seconds each, at most three at once, paused while the pointer is over them, then a 200 ms exit. `src/toasts.rs` draws it as a Rust root layer (`ToastLayer`), 0 by 0 while nothing shows, in Midnight's look (`toast-rate-limited.html`): `toast_width` 360, centred over the chat's timeline with the newest toast's bottom 8 above the timeline slot's bottom (just over the composer; centred 63 above the window's bottom while no slot is reported), `bg_3` with an `active` border, `radius_sm`, a 20-point round badge in the kind's colour (`red_2`, `green_2`, `yellow_2`, `blue_2`) holding a `text_0` glyph, the text 14 medium `text_2`, and a close button on hover. Toasts are overlays: the slot never moves for them (`ui::root::a_toast_floats_over_the_timeline_and_never_moves_its_rows`). The stack sits in a zgx `layer` (a 0 by 0 panel at the window's corner, no focus, the pointer passing through), mounted only while a toast shows (a mounted layer's host covers the window and hides every cursor under it; see "Cursors and the caret"), rebuilt on every push so it is raised over whatever dialog is open, the Luau settings and server settings dialogs included; toasts already showing do not replay their entrance (`ui::root::rust_dialogs_menus_and_toasts_open_above_the_settings_dialogs` also checks that Rust confirmations, the kick dialog and the member menu draw over both settings dialogs and take their clicks). `Link::place_slot` hands the layer the slot (`ToastLayer::set_area`). Anything in the window shows one with `toasts::show(kind, text)`; `toasts::copy(text, label)` copies and confirms ("Link copied", or an error when the clipboard refuses). Every copy action uses it (message menu, channel link, user ID, invite link).

Toasts leave on their own: every kind, errors included, lasts the same five seconds, and only the pointer over the stack holds them (leaving restarts the count from where it stopped). The expiry is a zgx timer task, which wakes the window by itself, so no input or redraw is needed. It is owned by the layer's outer component (`ToastLayer::view`), not by the stack inside the `layer` portal: that stack is rebuilt on every push and its tasks are cancelled with it, which left toasts on screen until a hover rescheduled the timer. `ui::root::a_toast_leaves_on_its_own_without_input_and_hovering_holds_it` drives real time with no input events (`ToastLayer::lasting` shortens the lifetime for it).

A `CommandRejected` reason becomes an error toast unless a surface that just acted shows it: the timeline's or the thread's action bar (15 seconds after a message action) or a composer (15 seconds after it sent, picked a GIF or sticker or confirmed a lock; `Composer::acted_recently`). Oxidcord toasts every rejection the same way. 45's plugin notice stays the red bar under the title bar.

The connection bar (`shell/connection_banner.luau`, in the timeline column, so the slot shrinks under it) is Midnight's (`connection-lost.html`): a `new_messages_bar_height` card inset `gap` from the chat panel's top and sides, `bg_3` with a `border` border, `radius_sm`, three 6-point dots, the text 14 medium (`text_3`, `red_2` while offline) and a quiet Retry at its right end. `bridge::ConnectionWatch` turns `state.session().connection` into `bridge::Connection`: `Live` (no banner), `Connecting` (first connect, "Connecting..."), `Reconnecting` ("Reconnecting in 3s..." while 07's backoff waits, "Reconnecting..." during an attempt, in `warning`), `Offline` after three failed attempts in a row ("You're offline. Retrying in 12s...", in `danger`), `Stopped` when the gateway gave up ("Disconnected from Discord: ...", no Retry) and `SignedOut`, which 21's login screen handles. The host publishes it as `session.connection` (`{ shown, state, text, tone, retry }`) and republishes the countdown once a second while it runs. Retry sends `Command::Reconnect`, as oxidcord's does: it hangs up a socket that is open, and while 07's backoff is waiting it changes nothing, so it never skips the backoff.

Transitions follow gpui-component's: `motion::modal` slides a dialog down 80 points and fades it in over 250 ms, `motion::popover` drops a popover 8 points and fades it over 150 ms (ease-out cubic), and toasts rise 24 points and fade over 400 ms in and 200 ms out. Every Rust modal and the expression picker use them. zgx closes a modal at once and draws its backdrop itself, so there is no exit animation and no backdrop fade; menus are zgx popup windows and do not animate. Reduced motion (`accessibility.reduced_motion` or the system's) keeps only the fades: `Motion`, provided at the root, carries it to `motion::Tween`. In Luau, `@components/motion` gives `duration(ms)`, 1 ms under reduced motion, for the rail morph, the unread pill and the search field; a tween reads it when it is built.

## Cursors and the caret

The pointer looks as it does in a browser (v1 86):

- The hand (`pointer`) over anything a click acts on: buttons, links, list rows (servers, channels, DMs, members, settings items), tabs, menu items, icon buttons, switches, radios, selects, chips, reactions, attachments.
- The I-beam (`text`) over inputs and text areas, and over selectable text such as the messages, which zgx gives by itself.
- `not_allowed` over a control that is shown but can't be used (a channel you can't open), or the arrow for a disabled button (`login.luau`'s buttons switch to `default` while disabled). A zgx `disabled` control or `menu_item` gets the arrow by itself.
- `ew_resize` or `ns_resize` over a splitter and `grab` over something that only drags. Kyoko has neither yet: rail tiles and roles drag to reorder but are clickable too, so they keep the hand, as in Discord.
- The arrow everywhere else: backgrounds, scrims, the title strip, text that isn't selectable.

Set the cursor once, in the kit piece: Luau `cursor = "pointer"` (`components/icon_button.luau`, `components/rail_tile.luau`, the buttons, rows and selects of `settings/kit.luau`), Rust `.cursor(Cursor::Pointer)` (`kit::button_view`, `kit::close_button`, `kit::switch`, `kit::radio_row`). A function (`cursor = function() ... end`, `reactive_style`) follows a disabled state. zgx-desktop falls back to the hand for a Button, Link, CheckBox or MenuItem role and the I-beam for a text input, but only from the deepest hovered node with listeners, so a button whose child listens (a hover spin, a tooltip) needs its cursor set.

zgx's cursor lookup (`Scene::cursor_at`) takes the topmost node under the pointer and ignores `pointer_events = "none"`, which presses honour. A full-window pass-through box above the shell therefore hides every explicit cursor under it while clicks still work, which is why kyoko showed no hand: the settings dialogs' window-sized measuring box (`settings/dialog.luau`) and the toast layer's always-open zgx `layer` covered the window. The measuring box is now `invisible` while its dialog is closed (it keeps its layout, so the size it measures is ready when the dialog opens), and the toast layer mounts only while a toast shows. Any new full-window layer must be 0 by 0, invisible or unmounted while it shows nothing. `ui::cursors::controls_show_the_hand_fields_the_i_beam_and_no_closed_layer_hides_either` builds the shell under every root layer, checks the hand, the I-beam and `not_allowed` on real controls, and names any hand-cursor control something else covers.

zgx draws an editor's caret but never blinks it. `src/caret.rs` blinks the focused editor's caret from a task at the app's root (started in `ui::run`, never rebuilt): each phase lasts Windows' caret blink time (`platform::caret::blink_time`, `GetCaretBlinkTime`, 530 ms by default), and the off phase swaps the caret's colour for transparent. An edit or caret move (the editor's revision or selection changes), a focus change or the window coming back restarts the cycle with the caret shown, so it stays solid while typing and blinks again a phase after the last key. With blinking turned off in Windows the caret stays solid. While the window is in the background zgx hides the caret itself and the blink never brings it back; read-only text has no caret. Capture runs don't blink, so parity shots are stable. `ui::cursors::the_caret_blinks_holds_while_typing_and_stays_hidden_while_the_window_is_away` drives the real composer with explicit times.

## Adding a screen

1. Add the module under `shell/` (or `components/` if it is reusable), styled only from `theme.luau`, with icons by name.
2. Publish what it needs from Rust as `<area>.<name>` shared values, declare them in `state.luau`, and add its actions to `actions.luau`.
3. Add its capture steps (`docs/parity.md`) and compare `pair.png` with oxidcord.
